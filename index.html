Glossary

Database Concepts Explained

⌕
ACID
Atomicity, Consistency, Isolation, Durability. The four properties that guarantee database transactions are processed reliably. If any part of a transaction fails, the entire transaction is rolled back.
transactionsSQLreliability
CAP Theorem
A distributed system can only guarantee two of three properties: Consistency (every read gets the latest write), Availability (every request gets a response), and Partition tolerance (system continues if nodes lose contact). NoSQL databases often trade C for A.
distributedNoSQLtheory
Index
A data structure (usually a B-Tree or Hash) that speeds up data retrieval without scanning every row. Indexes trade storage space and write speed for dramatically faster reads. Covering indexes include all queried columns to avoid table lookups entirely.
performanceSQLoptimization
Sharding
Horizontal partitioning of data across multiple database nodes. Each shard holds a subset of the data (e.g. users A-M on shard 1, N-Z on shard 2). Enables linear scale-out but adds complexity to cross-shard queries.
scalingdistributedNoSQL
Replication
Copying data from one database node (primary) to one or more replicas. Synchronous replication waits for all replicas to confirm before acknowledging a write. Asynchronous replication is faster but risks data loss if the primary crashes before syncing.
availabilityscaling
Normalization
The process of structuring a relational database to reduce data redundancy. 1NF eliminates repeating groups. 2NF removes partial dependencies. 3NF removes transitive dependencies. Over-normalization can hurt read performance; OLAP workloads often use denormalized star schemas.
schema designSQL
Eventual Consistency
A consistency model used in distributed systems where replicas are not immediately synchronized. Given enough time with no new updates, all replicas will converge to the same value. Used by Cassandra and DynamoDB to maximize availability and partition tolerance (per CAP).
NoSQLdistributedCAP
N+1 Query Problem
A performance anti-pattern where an application executes one query to fetch N records, then issues N additional queries to fetch related data for each. Fixed by using JOINs, eager loading (includes), or DataLoader batching. One of the most common ORM pitfalls.
performanceORManti-pattern
OLTP vs OLAP
OLTP (Online Transaction Processing) handles many short, concurrent read/write operations (e.g. booking a ticket). OLAP (Online Analytical Processing) handles complex queries over large datasets for reporting (e.g. monthly revenue by region). Different workloads often warrant different databases.
architectureworkloads
Foreign Key
A column that references the primary key of another table, enforcing referential integrity. The database rejects inserts or deletes that would leave orphaned records. Can be combined with CASCADE to automatically propagate deletes or updates to related rows.
SQLrelationshipsconstraints
Write-Ahead Log (WAL)
A durability mechanism where changes are written to a sequential log before being applied to the main data files. On crash recovery, the database replays the WAL to restore to a consistent state. PostgreSQL and MySQL both use WAL. Also enables logical replication.
durabilityrecoverySQL
Vector Embedding
A numerical representation of data (text, images, audio) as a list of floating-point numbers in high-dimensional space. Semantically similar items cluster together. The basis of semantic search and RAG pipelines. Typically generated by ML models like OpenAI text-embedding-3-small (1536 dimensions).
AIvector DBsemantic search
Interview Prep

Top 20 Database Interview Questions

All
Easy
Medium
Hard
01 What is the difference between SQL and NoSQL databases? ▾
Easy
SQL databases store data in structured tables with a fixed schema and use SQL for querying. They enforce ACID properties and are ideal for relational data with complex joins. NoSQL databases store data in flexible formats (documents, key-value, graphs) with dynamic schemas. They sacrifice some consistency guarantees (eventual consistency) for horizontal scalability and speed. Choose SQL for structured, transactional data; NoSQL for flexible, high-volume, or unstructured data.
02 What is an index and when should you use one? ▾
Easy
An index is a data structure that speeds up row lookups by storing a sorted copy of one or more columns alongside pointers to the full rows. Use indexes on columns you frequently filter, sort, or JOIN on. Avoid over-indexing: each index slows down INSERT/UPDATE/DELETE operations and consumes storage. A covering index that includes all queried columns eliminates table lookups entirely.
03 Explain the ACID properties with an example. ▾
Easy
Consider a bank transfer: debit $100 from Account A, credit $100 to Account B.

Atomicity: both operations happen or neither does. No partial transfers.
Consistency: balances can never go negative if the constraint says so.
Isolation: concurrent transfers don't see each other's mid-transaction state.
Durability: once the transaction commits, it survives a crash.
04 What is the difference between DELETE, TRUNCATE, and DROP? ▾
Easy
DELETE removes specific rows using a WHERE clause. It logs each row deletion and can be rolled back. Triggers fire. Slow on large tables.

TRUNCATE removes all rows from a table instantly by deallocating data pages. It cannot use WHERE, is minimally logged, and usually cannot be rolled back in MySQL (but can in PostgreSQL).

DROP removes the entire table definition and all its data permanently. Cannot be rolled back.
05 What is the N+1 query problem and how do you fix it? ▾
Medium
When an ORM fetches N parent records, then issues a separate query for each child relationship, you get N+1 total queries. Example: fetch 100 posts, then query comments for each post = 101 queries.

Fix it with: (1) eager loading / includes in your ORM, (2) a JOIN that fetches both in one query, (3) DataLoader batching in GraphQL, or (4) a subquery. Always profile your ORM's generated SQL in development.
06 Explain database normalization and when to denormalize. ▾
Medium
Normalization organizes data to reduce redundancy. 3NF (Third Normal Form) is the practical target for OLTP systems: no repeating groups, no partial dependencies, no transitive dependencies.

Denormalize for read performance when JOINs are too expensive: store pre-aggregated counts, copy frequently-read columns, or use a materialized view. Data warehouses (OLAP) use intentionally denormalized star/snowflake schemas because reads vastly outnumber writes.
07 What is the difference between optimistic and pessimistic locking? ▾
Medium
Pessimistic locking acquires a lock before reading data, preventing other transactions from modifying it until released (SELECT FOR UPDATE). Safe but reduces concurrency.

Optimistic locking reads data without locking, tracks a version number or timestamp, and checks at commit time that the version hasn't changed. If it has, the transaction retries. Better for read-heavy workloads with infrequent conflicts.
08 How would you design a database schema for a Twitter-like feed? ▾
Medium
Core tables: users (id, handle, bio), tweets (id, user_id, content, created_at), follows (follower_id, following_id), likes (user_id, tweet_id).

Fan-out on write: when a user tweets, pre-compute feeds for followers by writing tweet IDs into a feed table. Expensive for celebrities (millions of followers), so hybrid: pre-compute for normal users, merge celebrity tweets at read time. Use Redis sorted sets for hot feeds, PostgreSQL for storage.
09 What is connection pooling and why does it matter? ▾
Medium
Opening a new database connection is expensive: TCP handshake, authentication, session setup. Connection pooling maintains a pool of open, reusable connections. Applications borrow a connection from the pool, use it, and return it rather than opening and closing connections per request.

PgBouncer (PostgreSQL), ProxySQL (MySQL), and most ORM frameworks include pooling. Without pooling, a traffic spike that opens thousands of connections can exhaust PostgreSQL's max_connections limit and crash the database.
10 Explain the CAP theorem with a real distributed system example. ▾
Hard
In a distributed system, a network partition means some nodes can't talk to others. You must choose: do you return a stale (possibly inconsistent) response (AP), or return an error until the partition heals (CP)?

Cassandra chooses AP: it returns data from available nodes even if replicas haven't synced, accepting eventual consistency. This is right for Netflix watch history. ZooKeeper chooses CP: it refuses reads/writes if quorum can't be reached. This is right for distributed locks. PostgreSQL is CA but not partition-tolerant in a distributed sense, which is why CockroachDB was built.
11 How does a B-Tree index work internally? ▾
Hard
A B-Tree is a self-balancing tree where each node holds multiple keys in sorted order and pointers to child nodes or data pages. Lookups traverse from root to leaf in O(log n) time. Range scans are efficient because leaf nodes are linked in order.

For a single-column index on email, PostgreSQL builds a B-Tree of email values + heap tuple IDs (ctid). For a multi-column index (a, b), only queries filtering on a or (a AND b) benefit. Queries filtering only on b cannot use the index (leftmost prefix rule).
12 What is MVCC and how does PostgreSQL implement it? ▾
Hard
Multi-Version Concurrency Control keeps multiple versions of each row so readers never block writers and writers never block readers. In PostgreSQL, each row version (tuple) has xmin (transaction that created it) and xmax (transaction that deleted it). A transaction only sees rows where xmin committed before the transaction started and xmax is empty or committed after.

The downside is dead tuples accumulating. VACUUM reclaims storage by removing tuples no longer visible to any active transaction. autovacuum runs this automatically but can lag under heavy write workloads.
